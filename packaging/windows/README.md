# Windows packaging

## Current artifact

The release workflow produces `Tokeni-Bar-Windows-<version>.zip` and its SHA-256
file after the Windows tests, release build, and package validation pass. It publishes
both files in the same GitHub Release as the macOS assets. Extract the archive and run
`TokeniWindows.exe`; the package is portable and does not need a machine-wide
installation. The archive includes the executable, native DLLs, Swift runtime DLLs,
SwiftPM resource bundles emitted by the release build, and the complete companion
sprite catalog under `Resources\CompanionAssets`. It also includes the pinned official
SQLite x64 command-line shell under `Tools\sqlite3.exe` and its provenance notice.

릴리스 workflow는 Windows 테스트·release 빌드·패키지 검증을 통과한 뒤
`Tokeni-Bar-Windows-<version>.zip`과 SHA-256 파일을 만들고 macOS 파일과 같은
GitHub Release에 게시합니다. 압축을 푼 뒤 `TokeniWindows.exe`를 실행하면 되며,
시스템 전체 설치가 필요 없는 portable 패키지입니다. release 빌드에서 나온 실행
파일·native DLL·SwiftPM resource bundle과 `Resources\CompanionAssets`의 companion
sprite catalog를 함께 포함합니다. 공식 SQLite x64 command-line shell도 고정된
버전으로 `Tools\sqlite3.exe`에 포함하며 출처 고지를 함께 배포합니다.

## Scope and limitations

Published release artifacts require RSA code signatures from Microsoft Artifact
Signing on the app executable and otherwise-unsigned Swift runtime libraries. The
release workflow authenticates through GitHub OIDC, verifies every packaged executable
and DLL before rebuilding the ZIP, and refuses to publish when signing is unavailable.
Pull-request artifacts remain unsigned validation builds. The packaged SQLite metadata
preserves its reviewed upstream hash and records the final packaged hash separately
after signing.

게시 release artifact는 app executable과 기존에 서명되지 않은 Swift runtime library에
Microsoft Artifact Signing의 RSA code signature를 요구합니다. Release workflow는
GitHub OIDC로 인증하고 ZIP을 다시 만들기 전에 패키지의 executable과 DLL을 모두 검증하며,
서명할 수 없으면 게시를 중단합니다. Pull request artifact는 서명되지 않은 검증용 build로
유지합니다. 패키지의 SQLite metadata는 검토된 upstream hash를 보존하고 서명 후 최종
패키지 hash를 별도로 기록합니다.

Repository release environment must provide the `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`,
and `AZURE_SUBSCRIPTION_ID` secrets, plus the `AZURE_ARTIFACT_SIGNING_ENDPOINT`,
`AZURE_ARTIFACT_SIGNING_ACCOUNT`, and `AZURE_ARTIFACT_SIGNING_PROFILE` variables. The
federated identity must be restricted to this repository's release environment and have
the Artifact Signing Certificate Profile Signer role.

Repository release environment에는 `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`,
`AZURE_SUBSCRIPTION_ID` secret과 `AZURE_ARTIFACT_SIGNING_ENDPOINT`,
`AZURE_ARTIFACT_SIGNING_ACCOUNT`, `AZURE_ARTIFACT_SIGNING_PROFILE` variable이 필요합니다.
Federated identity는 이 repository의 release environment로 제한하고 Artifact Signing
Certificate Profile Signer role을 부여해야 합니다.

The separate `Tokeni-Bar-Windows-<version>-Setup.exe` installs for the current user,
creates a Start menu entry, and registers an uninstaller. It needs no administrator
rights. Settings, history and companion state remain outside the installation and
are preserved on uninstall. The installer is built with Inno Setup 6.

별도의 `Tokeni-Bar-Windows-<version>-Setup.exe`는 관리자 권한 없이 현재 사용자용으로
설치하고 시작 메뉴와 제거 프로그램을 등록합니다. 설정·기록·펫 상태는 앱 설치 폴더
밖에 저장되며 제거 후에도 유지됩니다. 설치 파일은 Inno Setup 6으로 만듭니다.

Settings includes manual update checks and opt-in automatic checks. Installing an
update requires the registered installation and valid Authenticode signatures with
the same publisher on the running app and downloaded installer. The updater checks
the release checksum, waits for the app to quit, backs up application files, installs,
and runs the runtime smoke check. Failed checks restore the previous files. Backups
and recovery status are retained under LocalAppData/TokeniBarUpdate. A still-running
installer is never interrupted by rollback. Preview/portable builds cannot use the
signed installation path; public signing and its complete end-to-end validation need
the release identity to be configured.

설정에서 수동 업데이트 확인과 자동 확인을 선택할 수 있습니다. 업데이트 설치는 등록된
설치 버전에서 실행하며, 앱과 설치 파일의 유효한 서명·동일 발행자·릴리스 체크섬을 확인합니다.
종료 대기·백업·설치 후 실행 검사를 진행하고 실패하면 이전 앱 파일로 복구합니다.
실행 중인 설치 프로그램은 복구 작업으로 중단하지 않습니다. 미서명 검증용 빌드와 portable
버전에서는 서명된 설치 경로를 사용할 수 없습니다. 정식 서명 및 전체 업데이트 검증에는
릴리스 서명 계정 설정이 필요합니다.

Build and verify an installer after packaging:

```powershell
./Scripts/build_windows_installer.ps1 -Version 1.2.3 -PackageDirectory ./dist/Tokeni-Bar-Windows-1.2.3 -OutputDirectory ./dist
./Scripts/test_windows_update.ps1
# Run only in a clean account without an existing Tokeni Bar installation:
./Scripts/test_windows_installer.ps1 -Installer ./dist/Tokeni-Bar-Windows-1.2.3-Setup.exe
```

The package is generated by `Scripts/package_windows.ps1`. It accepts a release
directory from `swift build --show-bin-path`, Swift runtime library directories, and
the explicitly acquired SQLite executable. It
validates the semantic version, refuses unsafe output roots, and only removes its own
staging directory and archive. The package step validates every manifest-referenced PNG
as a 512x384 8x6 sprite sheet, and the CI job repeats that check after extracting the ZIP.

패키지는 `Scripts/package_windows.ps1`이 생성합니다. `swift build --show-bin-path`의
release 디렉터리, Swift runtime library 디렉터리와 명시적으로 획득한 SQLite 실행
파일을 입력으로 사용합니다. semantic version을
검증하고 위험한 출력 루트를 거부하며 자신이 만든 staging 디렉터리와 archive만
삭제합니다. 패키지 단계에서는 manifest가 참조하는 모든 PNG가 512x384·8x6 sprite
sheet인지 검증하고, CI에서도 ZIP을 풀어 같은 검사를 반복합니다.

SQLite 3.53.4 is downloaded only from its exact official sqlite.org URL. Both a pinned
SHA-256 and SQLite's published SHA3-256 must match before the acquisition script extracts
the single `sqlite3.exe` entry. The executable must identify as an x64 PE and report the
pinned version. Updating SQLite therefore requires a reviewed change to
`packaging/windows/sqlite-tools.json`; CI never discovers a mutable latest version and
the application never falls back to a `sqlite3.exe` found on `PATH`.

SQLite 3.53.4는 정확히 고정한 공식 sqlite.org URL에서만 다운로드합니다. 획득 script는
고정 SHA-256과 SQLite가 게시한 SHA3-256이 모두 일치할 때만 단일 `sqlite3.exe` entry를
추출합니다. 실행 파일은 x64 PE이며 고정 버전을 보고해야 합니다. 따라서 SQLite
업데이트에는 `packaging/windows/sqlite-tools.json`을 검토하여 변경하는 절차가 필요하고,
CI는 변경 가능한 latest 버전을 찾지 않으며 앱은 `PATH`의 `sqlite3.exe`로 fallback하지
않습니다. SQLite는 public domain이며 배포 출처는 `THIRD-PARTY-NOTICES.txt`에 기록합니다.

## CI 범위

Windows 전용 pull request는 Windows build·package 검증만 실행하고, SwiftPM build
cache를 재사용합니다. 전체 macOS CI는 공통 코드나 macOS 코드가 변경될 때만
실행됩니다. Windows workflow를 `workflow_dispatch`로 직접 실행하면 Windows 전용
업데이트 설치·tray 상세 화면 테스트도 함께 실행됩니다.

Windows-only pull requests run the Windows build and packaging validation and reuse the
SwiftPM build cache. The full macOS CI runs only when shared or macOS code changes.
Dispatching the Windows workflow manually also runs focused Windows update-installer and
tray-detail tests.

After validating the archive layout and companion sprite sheets, CI extracts the ZIP
into a unique temporary directory and starts the packaged executable in its offline
`--smoke-test` mode. This verifies that the shipped runtime DLLs can load, companion
resources resolve relative to the executable, and the provider-neutral presentation
layer can produce deterministic output. The same smoke step runs the packaged SQLite
executable against a sanitized temporary database, checks read-only JSON output, and
verifies that the database bytes did not change. Each process has a bounded timeout.

archive 구조와 companion sprite sheet를 검증한 뒤 CI는 ZIP을 고유한 임시 디렉터리에
풀고 패키지의 실행 파일을 offline `--smoke-test` 모드로 시작합니다. 이를 통해 배포된
runtime DLL을 불러올 수 있는지, 실행 파일 기준으로 companion resource를 찾는지,
provider-neutral presentation 계층이 결정적인 출력을 만드는지 확인합니다. 프로세스에는
제한 시간이 있으며 CI는 명시적인 종료 코드와 고정된 성공 marker를 검사합니다. 같은
단계에서 패키지의 SQLite를 정제된 임시 database에 실행해 read-only JSON 결과와 database
byte가 변경되지 않았는지도 확인합니다.

The smoke mode does not instantiate providers, scan a user profile, read credentials or
usage logs, contact a network, or assert interactive tray behavior. Tray visibility,
notifications, overlays, DPI, multiple monitors, and Explorer restart recovery still
require an interactive Windows test environment.

smoke mode는 provider를 생성하거나 사용자 profile을 검색하지 않으며 credential 또는
usage log를 읽거나 network에 연결하지 않고 interactive tray 동작도 검증하지 않습니다.
tray 표시, 알림, overlay, DPI, 다중 monitor 및 Explorer 재시작 복구는 여전히 interactive
Windows 테스트 환경에서 확인해야 합니다.

Right-click the tray icon to refresh usage, toggle per-user startup, or send a test
notification. Automatic update installation remains disabled because the portable ZIP
does not yet provide an installer and rollback contract.

tray icon을 마우스 오른쪽 버튼으로 클릭하면 사용량을 새로 고치고, 현재 사용자 기준
자동 시작을 켜거나 끄고, 테스트 알림을 보낼 수 있습니다. Portable ZIP에는 아직
installer와 rollback 계약이 없으므로 자동 업데이트 설치는 비활성화되어 있습니다.

The same menu can show or hide the companion overlay. This layer applies pending awards
from the provider-neutral growth ledger after each verified refresh, persists the shared
companion state before acknowledging an award, and updates the overlay from that state.
If the asset root is missing or a sheet cannot be decoded, the native fallback renderer
remains available.

같은 메뉴에서 companion overlay를 표시하거나 숨길 수 있습니다. 검증된 갱신마다
provider-neutral 성장 ledger의 pending award를 적용하고, award 완료를 기록하기 전에 공통
companion 상태를 저장한 뒤 overlay를 갱신합니다. 자산 경로가 없거나 sheet를 해석할 수
없으면 native fallback renderer로 안전하게 전환합니다.
