# 토큰 관측과 성장 에너지

## 1. 목표

성장 시스템에서 가장 중요한 것은 화려한 확률보다 “한 번 사용한 토큰이 정확히
한 번만 반영된다”는 신뢰다. 제공자마다 토큰 값의 범위와 초기화 시점이 다르므로
화면에 표시된 `totalTokens`를 그대로 합산하지 않는다.

## 2. 용어

- 관측값: 제공자 어댑터가 특정 범위의 누적 토큰과 시각을 함께 전달한 값
- 범위: 일간 누적, 전체 누적, 세션 누적 중 하나
- 관측 키: 같은 누적 카운터인지 구분하는 안정적인 불투명 식별자
- 일간 토큰: 중복을 제거한 뒤 로컬 달력 날짜에 귀속된 전체 제공자 합계
- 성장 에너지: 일간 토큰을 게임 진행 수치로 변환한 값
- 반영량: 이미 지급한 오늘 에너지와 새 목표 에너지의 차이

## 3. 관측 계약

각 제공자 어댑터는 성장용으로 다음 의미를 명확히 제공해야 한다.

- 관측 범위: `daily`, `lifetime`, `session`
- 누적 토큰: 음수가 아닌 정수
- 범위 식별자: 날짜 또는 해시 처리한 세션 식별자
- 관측 시각과 원본 데이터의 갱신 시각
- 데이터 출처와 신뢰 상태
- 해당 값이 완전한 누적인지, 일부만 관측한 값인지

UI용 토큰 표시와 성장용 관측 계약을 분리한다. “최신 세션”, “현재 컨텍스트”,
“이번 달 계정”은 모두 토큰 숫자이지만 서로 더할 수 있는 값이 아니다.

## 4. 현재 제공자별 준비 상태

| 제공자 | 현재 값의 의미 | 바로 사용할 수 있는 범위 | 필요한 보강 |
| --- | --- | --- | --- |
| Codex | 계정 일간 버킷 및 월간 합계 | 오늘 일간 버킷 | 로컬 날짜 일치와 지연 버킷 처리 |
| Claude Code | 오늘 로컬 세션 합계 | 오늘 일간 누적 | 같은 로그의 중복 제거 검증 |
| OpenCode | 전체 로컬 세션 누적 | 조건부 전체 누적 | 단조 증가 체크와 DB 교체 감지 |
| Gemini CLI | 최신 세션 누적 | 아직 보류 | 안정적인 세션 키 노출 |
| Grok | 현재 컨텍스트 토큰 | 아직 보류 | 세션 키와 컨텍스트 초기화 감지 |

새 성장 시스템은 일부 제공자의 불완전한 값을 억지로 포함한 상태로 출시하지
않는다. Gemini와 Grok은 안정적인 관측 키를 어댑터에서 만들고 테스트한 뒤
성장 대상으로 활성화한다. 준비되지 않은 값은 기존 사용량 UI에는 보여도 성장에는
포함하지 않고 그 이유를 표시한다.

## 5. 하나의 제공자에서 하나의 기준값

공식 API와 로컬 로그를 동시에 읽을 수 있어도 같은 사용을 두 번 더하지 않는다.
`ProviderRegistry`의 각 어댑터가 그 시점의 대표 성장 관측값 하나를 선택한다.

출처가 바뀌는 경우의 규칙은 다음과 같다.

1. 동일한 관측 키이면 이전 체크포인트와 차이만 반영한다.
2. 관측 키가 바뀌면 새 누적값을 기준선으로만 저장한다.
3. 완전한 오늘 일간 누적임이 보장되고, 그 날짜에 어떤 기준선도 없을 때만
   자정부터의 누적을 최초 반영할 수 있다.
4. 출처 전환으로 사라진 토큰은 차감하지 않는다.

## 6. 성장식

오늘의 중복 제거된 전체 토큰을 `T`라고 할 때 오늘의 목표 성장 에너지 `G(T)`는
다음과 같다.

```text
T = 0       → G(T) = 0
T > 0       → G(T) = floor(32 × log2(1 + T / 25,000))
```

일일 하드캡은 없다. `T`가 증가하면 `G(T)`는 감소하지 않으며 유한한 상한도
없다. 정수 에너지이므로 작은 토큰 증가는 다음 에너지 경계까지 같은 값일 수 있다.
토큰이 매우 큰 구간에서는 에너지 1을 얻는 데 필요한 추가 토큰이 늘어난다.

| 오늘 토큰 | 오늘 성장 에너지 |
| ---: | ---: |
| 10,000 | 15 |
| 25,000 | 32 |
| 50,000 | 50 |
| 100,000 | 74 |
| 250,000 | 110 |
| 500,000 | 140 |
| 1,000,000 | 171 |
| 2,000,000 | 202 |

이 계수는 확정값이 아니라 첫 밸런스 기준안이다. 실제 사용자의 원문 데이터는
수집하지 않고, 사용자가 원할 때 로컬 최근 기록을 대상으로 예상 기간을 계산하는
진단 화면이나 개발용 시뮬레이터로 조정한다.

## 7. 지급 알고리즘

성장은 토큰 델타에 매번 공식을 적용하지 않고, 날짜별 누적 토큰에 대한 목표값을
계산한다.

```text
새 지급량 = max(0, G(새 일간 토큰) - 그 날짜에 이미 지급한 에너지)
```

이 방식은 앱의 새로고침 횟수, 제공자 순서, 작은 델타의 반올림에 결과가 달라지는
문제를 막는다.

여러 제공자를 함께 쓰면 각 제공자의 검증된 일간 토큰을 먼저 합한 다음 공식을
한 번 적용한다. 제공자를 나누어 쓴다는 이유로 성장량이 달라지지 않는다.

## 8. 날짜와 지연 데이터

- 날짜 기준은 사용자의 현재 Gregorian 로컬 날짜다.
- 이미 닫힌 날짜는 시간대 변경이나 시계 역행으로 다시 열지 않는다.
- 완전한 일간 버킷이 늦게 도착하면 최대 3일 전까지 미지급 차이를 반영한다.
- 지연분은 관측된 날짜의 공식으로 계산하되 현재 펫에 “지연 반영” 이벤트로 지급한다.
- 세션/전체 누적만 있는 소스는 앱이 해당 날짜에 처음 본 값을 기준선으로 삼는다.
  날짜 경계를 가로질러 앱이 꺼져 있었다면 어느 날 사용했는지 추정하지 않는다.

## 9. 값이 줄거나 비정상일 때

- 누적값 감소: 지급한 에너지를 회수하지 않는다. 새 값이 이전 최고점을 넘을
  때까지 추가 지급을 보류한다.
- 음수, 정수 오버플로, 미래 날짜: 관측을 폐기하고 진단 상태로 남긴다.
- 비정상적으로 큰 점프: 다음 새로고침에서도 같은 범위와 값을 확인한 뒤 반영한다.
- 데이터 없음/오래됨: 성장 보류. 활동 시간으로 토큰을 만들어 대체하지 않는다.
- 제공자 파서 변경: 정제된 fixture와 중복·초기화 테스트 없이는 활성화하지 않는다.

## 10. 토큰 구성

가능하면 제공자가 보고한 canonical total을 사용한다. 입력, 출력, 캐시, 추론
토큰에 서로 다른 가중치를 주지 않는다. 모든 제공자가 같은 세부 항목을 제공하지
않기 때문에 가중치를 주면 플랫폼 중립성이 깨진다.

토큰량은 현재 펫 상태 파일에 넣지 않는다. 성장 계산용 체크포인트는 사용량
기록 계층에서 관리하고, 펫에는 지급 완료된 성장 에너지와 이벤트 식별자만 남긴다.
